# 产品说明书 — 把一款 APK 做成「新游戏制作材料包」

> 给谁看：要用这套工具的人、收到分析结果的人、决定做不做的人  
> 配套：`使用指南.md`（怎么跑） / `输出物规格.md`（交什么） / `完整度矩阵.md`（能深到哪）  
> 版本：v0.3（实现规格已锁定，见 `docs/impl/实现规格.md`）

---

## 0. 先把产品说清楚

这不是「APK 解包器」，也不是「一键还原可上架工程」，也不重打包原 APK。

交给别人的东西叫 **制作材料包**：

- `output/美术`：对照图 + 资源总清单
- `output/策划`：可开工的制作说明书（核心玩法、系统、关卡、图鉴），必须对齐机器事实源
- 关卡能列出、有证据才写摆法；没证据标未知
- 可以发给策划 / 程序 / 另一个 AI，**不必附带原 APK**

一句话：**对照策划 + 美术，用自己的引擎重做玩法相同的新游戏。**

---

## 1. 谁在用，谁在收

工具有两种人，不能混。

| 角色 | 诉求 | 失败长什么样 |
|---|---|---|
| **操作者** 跑命令的人 | 少装环境、输入缺什么要被提醒、失败能看懂 | 装了 8 个工具仍报 so 找不到；跑完一堆 hash 文件名 |
| **接收者** 看结果的人 | 3 分钟知道这游戏是什么；按工种打开对应章节 | 丢来 4GB 文件夹，没有导读 |
| **制作人** | 一页纸 + 完整度雷达 + 风险 | 被 200 页 GDD 淹没 |
| **策划** | 循环、表、关卡画廊、经济、付费点、FTUE | 只有美术墙 |
| **程序** | 引擎、热更、客户端/服务器分界、状态机、协议线索 | 只有散文 GDD |
| **美术/音频** | 命名干净的资源、图集关系、风格板 | `CAB-a1b2.png × 4000` |
| **AI Agent** | 稳定 JSON（GameIR）+ 证据 | 只有 HTML |

产品设计原则：**操作者面对向导，接收者面对解剖包，机器面对 IR。** 三套界面，同一份数据。

## 2. 别人拿去用时，真实会发生的事

上一版开发文档写的是理想流水线。交给外人用，第一周会撞上这些，必须在产品里处理，而不是当「用户不会用」。

### 2.1 输入往往是残的

国内安卓游戏很少是「一个 apk 搞定」：

- TapTap / 好游快爆 / 233 的 **XAPK**（apk + obb 打成 zip）
- 华为 / 小米的 **APKS** 分包
- Google 的 split：`base` + `unity` + `arm64` + `asset`
- `main.obb` / `patch.obb`
- 首次启动后才下载的热更（Addressables、自研 CDN、HybridCLR dll）
- 渠道包：包名不同、资源几乎相同
- UnityCN 加密、乐固/梆梆/360 加固

如果产品只收「一个 .apk」，外人第一次就会觉得工具是坏的。

**产品必须有输入体检。** 分析开始前先打分：

```
输入完整度  42/100
- 这是 38MB 的 Unity 壳，主资源不在包内
- 发现 Addressables catalog，远程 URL 已记录（不会自动去下载）
请补：① 同目录 OBB  ② 或模拟器里玩过一局后的
    Android/data/<package>/files 缓存目录
不补也可以继续，但关卡和资源覆盖率会很低。
```

缺材料时 **允许继续**，但封面用红字写清「本报告基于残缺输入」。这比静默出一个空报告重要。

### 2.2 用户不会装逆向工具链

Il2CppDumper、apktool、jadx、AssetRipper、UnityPy、adb、Frida 对策划和大多数程序都是灾难。

对外交付形态必须是下面之一（按优先级）：

1. **Docker 一条命令**（默认推荐）：工具版本钉死，可复现
2. **可分发的 CLI + 依赖检查**：缺什么打印安装命令，不装也能跑「浅分析」
3. 以后才考虑 GUI

没有容器化，这套东西只能在作者机器上跑，谈不上给别人用。

### 2.3 用户要的不是文件树，是一份能开会的东西

解包成功但交付失败，典型长这样：

```
jobs/xxx/extract/raw/sharedassets0/Texture2D/img_0x7f.png
```

接收者无法使用。所以 **对外交付物 ≠ job 工作目录**。

工作目录给操作者排错；对外是 `deliverable/`（见 `输出物规格.md`）：

- 有封面导读
- 有完整度雷达
- 资源是人能读的名字
- GDD 按工种拆文件
- 关卡是画廊不是 YAML
- 有「不要外传」声明、没有原包、没有密钥

### 2.4 完整是雷达，不是开关

「全面反编译」做不到布尔成功。对外只能承诺：

> 我们产出一份带完整度雷达的解剖报告。每一维 0–5 分，有证据条数，做不到的标明原因。

接收者 30 秒就能决定：这份材料够不够开会，要不要补 OBB 再跑，要不要上深分析。

## 3. 四种使用模式

给别人用必须预设模式，否则每个人都以为自己买到了「100% 还原」。

| 模式 | 给谁 | 耗时感 | 产出 | 默认要不要设备 |
|---|---|---|---|---|
| **brief** 速览 | 制作人、立项会 | 数分钟～半小时 | 一页纸、雷达、资源墙、关卡目录（能列就列） | 否 |
| **standard** 标准 | 策划 + 程序 | 数十分钟～数小时 | 完整解剖包 + GameIR | 否 |
| **deep** 深挖 | 要公式、要加密表、要手感 | 小时级，需人值守 | standard + 运行时明文 dump + 公式/模拟 | 是（可选） |
| **share** 交接 | 把已有 job 发给别人 | 分钟级 | 消毒后的 `deliverable.zip` | 否 |

命令形态：

```bash
gameaihack analyze game.xapk --mode standard --out ./jobs
gameaihack analyze game.apk --mode deep --device emulator-5554 --hotupdate ./cache
gameaihack share ./jobs/<id> --to ./GameName-autopsy.zip
```

`--mode brief` 必须在资源还没全部转码完时就能出封面（先索引后导出）。大包 2GB+ 不能让制作人干等到全部 PNG 导出。

## 4. 「全面」到底覆盖哪些层

资源 / 关卡 / 策划 是三个桶，不够。一款游戏要被别人理解，至少有 **五层**：

```
L1 表层     看见的：图、音、UI、文案、模型、动画
L2 内容     库里的：角色、敌人、物品、技能、关卡条目
L3 空间     摆出来的：关卡布局、波次、触发、摄像机
L4 规则     算出来的：公式、状态机、经济图、胜负、解锁
L5 意图     设计出来的：教学顺序、付费压力、循环、手感、测什么
```

上一版管线把 L1–L3 当主路径，L4 靠表，L5 靠 LLM 散文。给别人用时，L4/L5 才是策划愿意转发的部分。

对外承诺改成：

| 层 | 标准模式要做到 | 深挖模式加什么 | 明确做不到 |
|---|---|---|---|
| L1 | 可浏览资源墙、按类型筛选、尽量还原文件名 | 运行时解开加密图/音 | 商业 Shader 100% 还原成可编辑图 |
| L2 | 表可打开、列有语义、实体模板对齐 | protobuf schema 推断加强 | 服务器库存里的时装/关卡 |
| L3 | 关卡目录 + 能画的画出 + 不能画的给实体计数 | 3D 俯视/glTF 预览 | 服务端随机副本的实时布局 |
| L4 | 经济图、进度图、UI 跳转、能找到的公式 | 战斗/经济模拟器跑一遍做校验 | 反编译出全部 IL2CPP 源码 |
| L5 | 循环、FTUE、付费点、广告点、手感清单、事件列表 | 结合真机流程录像对齐（人工） | 编造世界观 Lore、作者访谈级「为什么」 |

**L5 的「意图」只允许从证据推。** 教学顺序来自首关机制引入；付费压力来自 FTUE 里第一次弹出商店的位置；「测什么」来自打点事件名。推不出来就写未知，不写鸡汤。

## 5. 策划还原的完整本体（给接收者的目录）

标准模式的策划部分，固定按下面 20 维出雷达和章节。缺维 = 产品没做完，不是「以后再说」。

| # | 维 | 接收者拿来干什么 | 主要证据从哪来 |
|---|---|---|---|
| 1 | 身份证 | 30 秒定位品类、视角、单局时长、平台 | 包名、UI、商店文案、屏幕方向 |
| 2 | 表现语言 | 美术/镜头/音频风格对齐 | 相机组件、图集、BGM 列表 |
| 3 | 操作与手感 | 复刻手感 | Input、coyote、缓冲、镜头阻尼、震屏、顿帧 |
| 4 | 玩家动词 | 玩家到底能做什么 | 按钮、技能表、角色控制器 |
| 5 | 内容库 | 做表、估工作量 | 物品/敌人/技能/掉落表 |
| 6 | 空间与关卡 | 关卡设计评审 | Scene/Tilemap/棋盘 JSON |
| 7 | 胜负与规则 | 一局怎么结束 | 关卡表、结算 UI、代码枚举 |
| 8 | 对局解析 | 战斗/消除/建造怎么结算 | 公式、技能时间轴、伤害类型 |
| 9 | 成长 | 长线为什么留 | 经验、装备、收集、账号等级 |
| 10 | 经济 | 数值与产销 | 货币、掉落、商店、转化 |
| 11 | 商业化 | 风险与对照 | IAP sku、广告位、通行证、抽卡 |
| 12 | 社交 | 是否要做联机/排行 | 好友、公会、PVP 入口 |
| 13 | 叙事与文案 | 语气、本地化量 | loc 表、剧情、引导句 |
| 14 | 新手 FTUE | 前 3 分钟 / 前 3 关 | 引导 UI、前 N 关机制引入 |
| 15 | 界面结构 | 重做信息架构 | Prefab 树、跳转、红点 |
| 16 | 活动运营 | 是否有 Live ops | 活动表、日历、赛季 |
| 17 | 客户端/服务器 | 哪些规则改了也没用 | 网络 API、错误码、空关卡壳 |
| 18 | 表现反馈（Juice） | 打击感清单 | 粒子、HitFlash、CameraShake |
| 19 | 埋点意图 | 官方自己关心什么 | `Track`/`LogEvent` 事件名 |
| 20 | 技术骨架 | 重建可行性 | 引擎、热更、分包、加固 |

每一维输出三块，格式锁死，方便别人抽查：

```
结论（短）
证据（路径 / 表 / 代码符号）
缺口（为什么不是 5 分）
```

雷达画在封面。制作人只看雷达和缺口；策划看 4–16；程序看 3、8、17、20。

## 6. 三种图，比 GDD 正文更值钱

散文谁都会写。给别人用，要默认生成这些图（失败就空图 + 原因）：

1. **核心循环图**  
   一局循环 / 一日循环 / 长线循环，三张，节点必须来自 UI 或系统名。
2. **经济图**  
   源 → 货币 → 汇，标注是否 IAP、是否广告。能看出通胀和墙。
3. **关卡进度图**  
   关卡节点、解锁边、Boss、教学关高亮。旁边附难度曲线（能算才画：例如敌人 HP 总和 / 关卡时长估计）。

加分图（standard 能抽就抽）：

- UI 跳转图（主界面出发）
- FTUE 时间线（前 10 分钟可能弹出的窗口）
- 付费点在进程中的位置（第几关第一次体力墙 / 第一次抽卡）

这些图进 HTML，同时导出 mermaid / svg，方便贴进别人的文档。

## 7. 校验：怎么证明策划不是编的

给别人用最大的信任问题是：LLM 写得很完整，但是假的。

产品层做三道闸，不只「提示词里写不要编」。

### 7.1 证据编译器

GDD 不是模型直接写 Markdown。流程是：

```
GameIR → DesignClaim[]（结构化主张）→ 渲染成章节
```

没有 `evidence` 的主张进不了「已确认」。假设只能进「假设 / 未知」。构建时扫描，违规即失败。

### 7.2 模拟器（standard 能跑就跑，deep 必跑）

有表就做最小模拟，用来打脸错误抽取：

- **战斗/对局**：用抽出的 HP/ATK 打一关，清关时间是否离谱（3 秒或 3 小时）
- **经济**：F2P 跑 7 天，体力/金币是否立刻卡死或无限膨胀
- **进度**：按解锁表走，第 N 关是否不可达

模拟结果写进报告「自洽性」一节。离谱就降低该维分数，而不是删数据——数据可能是对的，缺了服务器系数。

### 7.3 人工抽查清单（随包附带）

交接给别人时，附 10 条抽查题，接收者 15 分钟能验货：

1. 品类判断是否明显错（把三消写成 RPG）
2. 货币种类是否和商店 UI 一致
3. 第 1 关预览是否像那么回事
4. 第一次付费点是否真在那个界面
5. 雷达上 4 分以上的维，点开能否看到证据
6. 未知项是否在回避关键系统（例如明明有抽卡却写未发现）
7. 资源墙能否搜到主角
8. 包名/版本是否就是那个包
9. 是否误把渠道 SDK 广告当成游戏核心循环
10. share 包里是否误带了 APK 或密钥

## 8. 完整度怎么对别人讲（期望管理）

对外只讲这张表，细节见 `完整度矩阵.md`。

**引擎 × 模式 的诚实预期（不是 KPI）：**

| | Unity Mono 2D | Unity IL2CPP | Cocos Lua | Unreal 手游 | 加固 + 热更 |
|---|---|---|---|---|---|
| brief 资源墙 | 高 | 高 | 中高 | 中 | 中（assets 常仍在） |
| 表与数值 | 高 | 中（靠 dummy） | 高（json/lua） | 中（DataTable） | 低～中 |
| 关卡画出 | 中高 | 中 | 中高（tmx/json） | 中低 | 低 |
| 公式/手感 | 中 | 低（需 deep） | 中 | 低 | 低 |
| 策划循环/付费 | 中高 | 中高（UI+表够用） | 中高 | 中 | 中 |
| 可重玩关卡 | 低（二期） | 低 | 低 | 低 | 低 |

**会看起来「空」的游戏类型**（产品要预先警告）：

- 强服务端：MOBA、开放世界、卡牌对战的牌库/关卡在服务器
- 重热更：安装包只有壳，玩了才有内容
- 强加密 + 无设备：deep 模式被关掉时表是二进制

警告文案写在封面，不要写在最后一页。

## 9. 给别人用的交互，必须像向导

### 9.1 操作者：分析前

```
gameaihack doctor          # 环境
gameaihack inspect foo.apk # 不写盘的体检：引擎、是否壳、缺不缺 OBB
gameaihack analyze ...     # 真正跑
```

`inspect` 免费、快、可给不懂的人跑。它的输出就应该能转发：「这是 Unity IL2CPP，缺 OBB」。

分析中：

- 终端进度按阶段，预估剩余（不准也要有）
- 每阶段结束写一条人话：`[levels] 索引到 86 关，重建了 12 关到 L2，其余是棋盘二进制未解码`
- 支持 Ctrl+C 后 `--resume`，大包不能从头来

### 9.2 接收者：打开即懂

`deliverable/README.md` 前 30 行固定结构（模板在 `docs/templates/交付包README.md`）：

1. 这是什么游戏（一句话）
2. 完整度雷达（文字版）
3. 你该打开哪个文件（按角色）
4. 本包基于什么输入（缺不缺 OBB）
5. 不要做什么（不要分发原画、不要当可商用素材）

HTML `index.html` 双击即开，不依赖本地服务器。这是给别人用的硬条件。

### 9.3 机器：稳定契约

Agent / 下游重建工具只读：

- `machine/game.ir.json`
- `machine/claims.json`
- `machine/coverage.json`

schema 版本化。升主版本才允许破字段。别人基于 IR 写重建器时，不能随手改字段名。

## 10. 交接与合规（给别人用的前提）

操作者在 `analyze` 第一次跑时要经过确认（可用 `--i-have-rights` 跳过交互，但日志里留下）：

- 我有权分析这个包（自有 / 书面授权 / 公司竞品合规流程）
- 我不会把原包和密钥放进分享包
- 接收者被告知：资源有版权，仅内部研究

`share` 命令必须做消毒：

- 排除 `*.apk *.obb *.so` 原包与库（可选保留哈希清单）
- 排除任何 `*key* *secret*`
- 大图可 `--thumbs-only`（只出缩略图，原图留在操作者机器）
- 封面加水印文案：内部分析，禁止二次分发
- 生成 `LEGAL.txt`

没有 `share` 消毒，就不要让人把 `jobs/` 整个打 zip 发出去——那是把原包和密钥一起寄走。

本工具 **不提供**：重打包、去广告、破解内购、外挂、通用脱壳 exploit、自动去 CDN 拉付费资源。

## 11. 产品形态与仓库边界

给外人的「产品」是三件套：

```
1. 运行时：Docker 镜像 / CLI
2. 一次分析的解剖包：deliverable.zip
3. 文档：本说明书 + 使用指南 + 完整度矩阵
```

不是给外人的：

- `jobs/*/extract/raw`（太大、太脏）
- 商业 APK 样本
- 密钥
- 未完成的 adapter

插件给「会写代码的别人」：

- 新引擎 adapter
- 新关卡解码器（某三消私有二进制）
- 新 DesignPass（例如你们公司只要商业化一章）

这才是可扩展的「给别人用」，而不是把作者的 notebook 拷走。

## 12. 成功标准（产品，不是工程）

把工具交给一个没写过这套代码的人，下列全部成立才叫能用：

1. `doctor` 能说明缺什么；Docker 路径下 `analyze` 能跑起来。
2. 只丢一个残缺 apk，封面会骂你缺 OBB，而不是出空报告装成功。
3. 制作人只看封面能复述品类、引擎、完整度、主要风险。
4. 策划不看二进制能讲清循环、货币、前 10 关在教什么。
5. 抽查 10 条「已确认」主张，至少 9 条能点到证据。
6. `share` 的 zip 不含 apk/密钥，双击 HTML 能看。
7. 雷达有空洞时，未知项能告诉下一步补什么材料或换 deep。

做不到第 2、5、6 条，就还是作者自用脚本，不是产品。
